実装計画を作成してください: $ARGUMENTS

## 成果物の要件

**本セッションの文脈を持たない別のエージェントが、この計画だけを読んで実装を完了できること。**

「前述のとおり」「先ほど決めたように」のような、この会話に依存する参照を書かないでください。この会話でしか分からない前提は、計画本文に明示的に書き出してください。

## 成果物の置き場所

計画は **ファイルに保存** します。チャットに出すだけでは、別セッションの実装者に渡せず上記の要件が成立しません。

- 保存先は `docs/plans/<yyyymmdd>-<slug>.md`。リポジトリに計画文書の既存の置き場所や命名規約があるなら、そちらに従う。
- `Write` ツールはこの計画ファイルの作成にのみ使う。**既存ファイルを上書きしない。**
- チャットには「一言でいうと」「設計判断の一覧」「保存先パス」だけを出す。全文は貼らない。
- 計画ファイルを成果物としてコミットするかはリポジトリの方針次第。**方針が不明なら、コミット対象に含めるかを人間に確認する。**

## 計画を書き始める前に

1. **対象の把握**: `$ARGUMENTS` が空なら、計画の対象を尋ねて停止する。GitHub Issue の番号・URL なら `gh issue view "$ARGUMENTS" --comments` で本文とコメントを取得する（要件はコメント欄で確定していることが多い）。ブランチ名やファイルパスなら該当箇所を読む。
2. **既存コードを読む**: 変更対象と、その周辺の既存実装・共通処理を特定する。同じ役割の関数を重複実装しないため、**再利用できる既存資産を先に洗い出す**。
3. **ライブラリ API の検証**: context7 MCP が使えるなら `resolve-library-id` でライブラリを特定し、ドキュメント取得ツールで API を確認する。使えない場合は公式ドキュメントを参照し、情報源を明示する。記憶に頼って書かない。

**要件不足のせいで決められない論点が2件以上ある場合は、計画を書き始めず `/grill-me` の実施を提案して停止する。** 「たぶんこうだろう」で埋めた前提の上に計画を積まない。

## 計画に必ず含める項目

小さな変更では該当しない節が出ます。**該当しない節は「該当なし」と書かずに省いてください。** ただし §10 は承認の判断材料なので、未確認事項がなければ「なし」と明記して必ず残します。

### 1. 概要

- 一言でいうと何をするのか
- 解決する課題（ビジネス要件）
- 対象外（今回やらないこと）

### 2. 変更対象ファイル一覧

ファイルごとに、新規 / 変更 / 削除の別と、変更内容を記述する。

### 3. 影響範囲

- 変更を受ける既存の呼び出し元
- 公開 API・型・スキーマの破壊的変更の有無
- マイグレーションとロールバック手順（該当する場合）

### 4. 実装ステップ

依存関係の順に番号を付けて列挙する。各ステップは単体で意味が通り、**途中で中断してもリポジトリが壊れない粒度**にする。

### 5. 設計判断

判断に迷いのあった箇所は `D-01` 形式の識別子を付け、**選択肢・採用した案・採用理由**を記述する。自明な判断は書かない。

### 6. ライブラリ API の使用方法（外部ライブラリを使う場合のみ）

正しい呼び出し方と **出典 URL** を併記する。

### 7. テスト方針

- テスト対象と、網羅するケース（正常系・異常系・境界値）
- 重要ロジックがテスト可能な構造になっているか

### 8. 品質管理手順

このリポジトリの Linter / Formatter / 型チェック / テストの実行コマンド。推測せず、`package.json`・`pyproject.toml`・CI 設定などから実際に確認して記載する。

### 9. 動作確認手順

人間が手元で結果を確認するための具体的な手順。

### 10. 未確認事項・確認したいこと

**承認前に人間に判断してほしい点を、ここ1箇所に箇条書きでまとめる。** 本文中に「未確認」と書いた箇所は、すべてこの節から辿れるようにする。承認する人間はここを読んで可否を判断するため、本文に散らしたままにしない。

## 進め方

- 計画を提示したら **そこで停止する**。実装には進まない。承認は人間が行う。
  （このスキルが有効な間は `Edit` が無効化されている。承認後の次のターンで解除される）
- **`AGENTS.md` の「可能な限り自走して完了まで進める」は、このコマンドには適用しない。** 本コマンドの成果物は計画のみであり、承認前に実装へ着手することは指示違反とする。実装は人間が `/implement-plan` を起動して開始する。
- 確認が取れなかった前提は「未確認」と明記し、§10 に集約する。埋めるために推測しない。
