# Domain Modeling

設計を進めながら、プロジェクトのドメインモデルを能動的に構築し、研ぎ澄ます。これは **能動的な** 規律である。用語に異議を唱え、エッジケースのシナリオを考案し、用語集と判断が固まった瞬間に書き留める。（語彙を確認するために単に `CONTEXT.md` を **読む** のは、このスキルではない。それはどのスキルでもできる一行の習慣にすぎない。このスキルが対象とするのは、モデルを消費するときではなく、**変更する** ときである。）

## ファイル構成

たいていのリポジトリはコンテキストを1つだけ持つ。

```
/
├── CONTEXT.md
├── docs/
│   └── adr/
│       ├── 0001-event-sourced-orders.md
│       └── 0002-postgres-for-write-model.md
└── src/
```

ルートに `CONTEXT-MAP.md` がある場合、そのリポジトリは複数のコンテキストを持つ。マップは各コンテキストの所在を示す。

```
/
├── CONTEXT-MAP.md
├── docs/
│   └── adr/                          ← システム全体に関わる判断
├── src/
│   ├── ordering/
│   │   ├── CONTEXT.md
│   │   └── docs/adr/                 ← このコンテキスト固有の判断
│   └── billing/
│       ├── CONTEXT.md
│       └── docs/adr/
```

ファイルは **遅延して** 作る。書くべき内容が出てきたときにだけ作成する。`CONTEXT.md` が存在しないなら、最初の用語が確定した時点で作る。`docs/adr/` が存在しないなら、最初の ADR が必要になった時点で作る。

## セッション中に行うこと

### 用語集と突き合わせて異議を唱える

ユーザーが使った用語が `CONTEXT.md` の既存の言葉と衝突する場合、即座に指摘する。「用語集では『キャンセル』を X と定義していますが、いまは Y の意味で使っているように見えます。どちらですか」

### 曖昧な言葉を研ぎ澄ます

ユーザーが漠然とした語や多義的な語を使ったら、正確な正典用語を提案する。「『アカウント』とおっしゃいましたが、Customer のことですか、User のことですか。この2つは別物です」

### 具体的なシナリオで議論する

ドメイン上の関係（概念どうしの関係）が話題になったら、具体的なシナリオでストレステストする。エッジケースを突くシナリオを考案し、概念どうしの境界についてユーザーに厳密な言明を迫る。

### コードと相互参照する

ユーザーが「これはこう動く」と述べたら、コードがそれに同意しているか確認する。矛盾を見つけたら表に出す。「コードは Order 全体をキャンセルしていますが、いま部分キャンセルが可能だとおっしゃいました。どちらが正しいですか」

### `CONTEXT.md` をその場で更新する

用語が確定したら、その場で `CONTEXT.md` を更新する。まとめて後回しにしない。発生した瞬間に捉える。書式は [CONTEXT-FORMAT.md](./CONTEXT-FORMAT.md) に従う。

`CONTEXT.md` には実装の詳細を一切含めない。`CONTEXT.md` を仕様書、下書き置き場、実装判断の記録場所として扱ってはならない。**これは用語集であり、それ以上のものではない。**

### ADR は控えめに提案する

ADR の作成を提案してよいのは、次の3条件がすべて満たされるときだけ。

1. **覆しにくい**: あとで考えを変えるコストが無視できない
2. **文脈がなければ驚く**: 将来の読み手が「なぜこうしたのか」と疑問に思う
3. **実際のトレードオフの結果である**: 現実的な選択肢が複数あり、特定の理由で一つを選んだ

どれか一つでも欠けるなら ADR は書かない。書式は [ADR-FORMAT.md](./ADR-FORMAT.md) に従う。
