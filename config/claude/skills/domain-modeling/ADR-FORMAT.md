# ADR の書式

ADR は `docs/adr/` に置き、連番で命名する。`0001-slug.md`、`0002-slug.md` のように。

`docs/adr/` ディレクトリは遅延して作る。最初の ADR が必要になったときにだけ作成する。

## テンプレート

```md
# {判断の短いタイトル}

{1〜3文: どういう文脈で、何を決め、なぜそう決めたか。}
```

これだけである。ADR は1段落で構わない。価値があるのは、判断が下された **という事実** と **その理由** を記録することであって、各セクションを埋めることではない。

## 任意のセクション

以下は、実際に価値を足すときにだけ含める。ほとんどの ADR には不要。

- **Status** フロントマター（`proposed | accepted | deprecated | superseded by ADR-NNNN`）: 判断が後から見直される場合に有用
- **Considered Options**（検討した選択肢）: 却下した案を覚えておく価値があるときだけ
- **Consequences**（結果・影響）: 自明でない下流への影響を明示する必要があるときだけ

## 採番

`docs/adr/` を走査して最大の既存番号を調べ、1を足す。

## ADR を提案してよいとき

次の3条件が **すべて** 満たされること。

1. **覆しにくい**: あとで考えを変えるコストが無視できない
2. **文脈がなければ驚く**: 将来の読み手がコードを見て「一体なぜこんなやり方をしたのか」と疑問に思う
3. **実際のトレードオフの結果である**: 現実的な選択肢が複数あり、特定の理由で一つを選んだ

覆しやすい判断なら書かない。どうせ覆すだけである。驚きがないなら、誰も理由を疑問に思わない。現実的な代替案がなかったなら、「当たり前のことをやった」以上に記録すべきものはない。

### 該当するもの

- **アーキテクチャの形**。「モノレポを採用する」「書き込みモデルはイベントソーシング、読み取りモデルは Postgres へ射影する」
- **コンテキスト間の連携パターン**。「Ordering と Billing は同期 HTTP ではなくドメインイベントで通信する」
- **ロックインを伴う技術選定**。データベース、メッセージバス、認証プロバイダ、デプロイ先。すべてのライブラリではなく、**差し替えに四半期かかるもの** に限る。
- **境界とスコープの判断**。「Customer のデータは Customer コンテキストが所有し、他のコンテキストは ID でのみ参照する」。明示的な「やらない」は「やる」と同じだけの価値を持つ。
- **自明な道からの意図的な逸脱**。「X という理由で ORM ではなく手書き SQL を使う」。まともな読み手なら逆を想定するであろうもの全般。これは、意図的だったものを次のエンジニアが「修正」してしまうのを防ぐ。
- **コードから見えない制約**。「コンプライアンス要件により AWS は使えない」「パートナー API の契約により応答時間は 200ms 未満でなければならない」
- **却下理由が自明でない代替案**。GraphQL を検討したうえで微妙な理由から REST を選んだなら記録する。さもないと半年後にまた誰かが GraphQL を提案する。
